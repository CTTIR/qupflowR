# qupflowR Java bridge

Java side of qupflowR: a small authenticated HTTP API on `127.0.0.1` that runs either inside
QuPath 0.7.0 (extension, host type `live`) or as a headless process started by R (worker,
host type `worker`). It is built separately from the R package and registered by `qp_setup()`.

Status: scaffold (task T01). The transport, discovery files, token, routing, error envelopes,
`GET /v1/health` and `GET /v1/capabilities` are implemented and tested. Every other endpoint of
protocol v1 is reported as unavailable (`reason_code: not_implemented`) by the capability report.

## Modules

- `bridge-protocol`: protocol version, build info, error-code registry, DTO records, the JSON
  decoding rules shared with R (`CanonicalJsonReader`, also behind `ProtocolJson.parse`), canonical
  JSON (`CanonicalJson`) and the Draft-07 subset schema validator (`SchemaValidator`, decision
  D022). Gson is compile-only.
- `bridge-core`: `java.base`-only loopback HTTP transport, bridge server, runtime files, token,
  router and the QuPath 0.7 adapter boundary. Depends on `bridge-protocol`; QuPath core, Gson and
  SLF4J are compile-only.
- `bridge-extension`: `QupflowrExtension`, menu *Extensions > qupflowR* and the bridge life cycle.
  QuPath GUI is compile-only.
- `bridge-worker`: `WorkerMain`, the Groovy bootstrap and the distribution with `launch.json`.
  QuPath core is compile-only.
- `bridge-fixtures`: the generator of synthetic fixture set 1 (TIFF, OME-TIFF and QuPath projects)
  used by `tools/fixtures.R`. Its JDK-only source set holds the formulas and expected values and is
  unit tested without QuPath; the `qupath` source set compiles against the jars of a local QuPath
  0.7.0 installation, pinned by sha256 (see `bridge-fixtures/README.md`). It is not part of the
  bundle.

The extension and worker jars contain only `io.github.cttir.qupflowr` classes plus
`META-INF/LICENSE` (and the extension service file). QuPath, JavaFX, Gson, SLF4J and Logback are
provided by the QuPath installation; `verifyJarContents` enforces this.

## Build

Requirements: a Java 25 JDK (development: `.tools/jdk-25`; toolchains are never downloaded). A
QuPath 0.7.0 installation is needed for the live smoke tests and for every task that compiles the
`qupath` source set of `bridge-fixtures` (`build`, `assemble`, `:bridge-fixtures:jar`): it is
taken from `-Pqupflowr.qupathHome=<dir>`, else `QUPFLOWR_QUPATH_HOME`, else `/opt/QuPath-v0.7.0`.
`test` and `bridgeBundle` do not need it.

```sh
cd <repository root>
. dev/toolchain.env
cd tools/bridge
./gradlew test                  # all unit tests (no QuPath installation or display needed)
./gradlew bridgeBundle          # extension jar, worker distribution, bundle zip
./gradlew verifyJarContents     # jar checks with negative controls
./gradlew build                 # compile, tests, strict Javadoc, jar checks, bundle, fixture
                                # generator jar (needs the QuPath installation, see above)
```

Outputs:

- `bridge-extension/build/libs/qupflowr-bridge-extension-<version>.jar`
- `bridge-worker/build/libs/qupflowr-bridge-worker-<version>.jar`
- `bridge-worker/build/distributions/qupflowr-bridge-worker-<version>.zip`
- `build/distributions/qupflowr-bridge-bundle-<version>.zip` and `.zip.sha256`

The shared error-code registry `inst/schema/protocol/v1/error-codes.json` is copied into
`bridge-protocol` at build time and the build fails if it is missing. When building from a copy of
this directory, pass `-Pqupflowr.schemaDir=<path to inst/schema>`.

Archives are reproducible: no file timestamps, fixed file order and permissions.

## Reproducibility and supply chain

- **Gradle wrapper 9.4.0.** `gradle/wrapper/gradle-wrapper.properties` pins
  `distributionSha256Sum=60ea723356d81263e8002fec0fcf9e2b0eee0c0850c7a3d7ab0a63f2ccc601f3`. The
  wrapper files were generated by Gradle 9.4.0 itself (`gradle wrapper --gradle-version 9.4.0
  --distribution-type bin --gradle-distribution-sha256-sum 60ea72...`); `gradle-wrapper.jar` has
  sha256 `55243ef57851f12b070ad14f7f5bb8302daceeebc5bce5ece5fa6edb23e1145c`, the published value
  for Gradle 9.4.0.
- **QuPath baseline.** The settings plugin `io.github.qupath.qupath-extension-settings` 0.2.1
  provides the QuPath 0.7.0 version catalogue (`libs`), including JDK 25, Gson 2.13.2 and JUnit.
- **Dependency locking.** All configurations are locked in strict mode (`gradle.lockfile` per
  module, `settings-gradle.lockfile` for the catalogue). The classpath of the settings plugin itself
  is pinned by the plugin version and covered by verification metadata; Gradle writes no lock state
  for it.
- **Dependency verification.** `gradle/verification-metadata.xml` holds sha256 checksums of every
  resolved artifact and metadata file; `org.gradle.dependency.verification=strict`.

After a deliberate dependency change (or when adding a module such as `bridge-fixtures`), refresh
locks and checksums and review the diff. Generate the checksums with an empty Gradle user home: a
cold resolution downloads metadata files (for example parent POMs) that a warm cache never touches,
and those must be listed too.

```sh
./gradlew --write-locks resolveAndLockAll            # lock state for every configuration
GRADLE_USER_HOME="$(mktemp -d)" ./gradlew --write-verification-metadata sha256 \
  resolveAndLockAll build bridgeBundle              # adds missing checksums (network needed)
./gradlew build bridgeBundle                         # must pass with verification enabled
```

Platform note: compiling the extension resolves JavaFX and JavaCPP artifacts with a platform
classifier. The committed checksums were generated on Linux x86_64; other platforms need their
classifier artifacts added to the verification metadata before the extension builds there.

## Transport rules (bridge-core)

- IPv4 `127.0.0.1`, random port, one virtual thread per connection, `Connection: close`.
- Limits: request line 8 KiB, header block 16 KiB, 100 headers, body 16 MiB absolute and a smaller
  limit per route (health and capabilities accept no body), `Content-Length` framing only.
- Deadlines: idle read 5 s, headers 10 s after accept, whole request 30 s.
- Precedence before any body byte: request syntax and framing, Host, target, Expect, Origin,
  bearer token, route and method, route body limit; `100 Continue` only after admission.
- At most 64 counted connections. A connection counts until its response is written; the slot is
  released before the bounded linger. When the cap is reached, the oldest connection that is stalled
  in its header phase (no unread input, and either some bytes received or silent for more than
  250 ms) is evicted with `503 HOST_BUSY` (`reason: evicted_header_phase`, `Retry-After: 1`).
  Only if nothing is evictable does the new connection get `503 HOST_BUSY`
  (`reason: connection_limit`).
  Clients that hold partial requests open (bytes received, then stalled) can therefore not block
  complete, authenticated requests (unit tests hold 100 such connections, a verification run
  200). Silent sockets are only evictable after 250 ms: a local process that keeps reconnecting
  silent sockets faster than that holds every slot for as long as it runs, and new connections,
  including authenticated ones, get retryable `503 HOST_BUSY` answers during that time. A
  verification run with 200 reconnecting silent sockets answered 259 of 277 health polls with
  `HOST_BUSY`, and a client retrying with capped exponential backoff did not get through within
  15 s. The listener is bound to `127.0.0.1`, so only local processes can do this; clients must
  treat `HOST_BUSY` as retryable and give up with a clear message after their own deadline.
- Bodies are streamed to route handlers, never buffered by the server.
- Request logs name the matched route template and a known method, never raw paths, queries,
  header values or the token.

Error responses use the registry: HTTP status, `message_key` and `retryable` come from
`error-codes.json`; `details.reason` is a machine-readable code and `413` adds `limit_bytes`.

## Discovery files

```
<runtime dir>/            0700, owned by the current user (checked)
  instances/              0700
    <instance_id>.json    manifest 0600 (host_type, pid, process_start_time, instance_id, host,
                          port, qupath_version, bridge_version, protocol_version, token_file,
                          created_at); never contains the token
    <instance_id>.token   256-bit base64url token 0600
```

Files are written atomically (temporary file, fsync, atomic move). The manifest is published last
and removed first on stop.

Runtime directory resolution of the extension (`RuntimeDirectories`); the worker always receives
its directory explicitly (`--runtime-dir` or `-Dqupflowr.runtimeDir`):

1. system property `qupflowr.runtimeDir`
2. environment variable `QUPFLOWR_RUNTIME_DIR`
3. Linux/Unix: `$XDG_RUNTIME_DIR/qupflowr` if `XDG_RUNTIME_DIR` is absolute, otherwise
   `$XDG_CACHE_HOME/qupflowr/runtime`, otherwise `~/.cache/qupflowr/runtime`
4. macOS: `~/Library/Caches/qupflowr/runtime`
5. Windows: `%LOCALAPPDATA%\qupflowr\runtime`, otherwise `~\AppData\Local\qupflowr\runtime`

A shared temporary directory is never used. The R client must apply the same order.

## Extension

Install `qupflowr-bridge-extension-<version>.jar` into the `extensions` directory of the QuPath
user directory. Menu *Extensions > qupflowR*: start, stop and a status line. System properties:

| Property | Effect |
|---|---|
| `qupflowr.autostart=true` | start the bridge while the extension installs (background thread) |
| `qupflowr.runtimeDir=<dir>` | runtime directory (see above) |
| `qupflowr.language=de\|en` | menu language, default German |
| `qupflowr.bridge.logRequests=true` | log every request outcome at INFO |

The bridge refuses to start unless QuPath reports exactly 0.7.0. A JVM shutdown hook removes the
discovery files when QuPath exits. QuPath may skip the extensions directory silently when no inotify
instance is available; diagnostics must treat "QuPath runs but no manifest appears" as a possible
cause.

## Worker

`WorkerMain --runtime-dir <dir>` serves the bridge until standard input reaches end of file (exit
0) or the JVM receives SIGTERM (exit 143); both remove the discovery files. Standard output carries
only JSON event lines: `{"event":"ready","instance_id":...,"manifest":...}` or
`{"event":"failed","reason":...}`. `WorkerMain --version` prints the bridge, protocol, Java and
detected QuPath versions (exit 0 when QuPath 0.7.0 is on the class path, 3 otherwise). Exit codes:
0 stopped, 1 start failed, 2 usage, 3 unsupported QuPath, 143 SIGTERM.

The distribution zip contains `lib/<worker jar>`, `bootstrap/qupflowr-worker-bootstrap.groovy`,
`config/logback-worker.xml`, `launch.json`, `checksums.sha256`, `LICENSE` and `THIRD-PARTY.md`.
`launch.json` describes two launch profiles with placeholders (`<DIST>`, `<QUPATH_HOME>`, `<JAVA>`,
`<RUNTIME_DIR>`, `<PREFS_DIR>`, `<TMP_DIR>`, `<JAVACPP_CACHE_DIR>`, ...). Both profiles set
`-Djava.awt.headless=true -Dprism.order=sw` and private prefs, temporary and JavaCPP cache
directories, so QuPath code in the worker never writes into the user's home:

- `java` (preferred): `<JAVA> <jvm_options> -cp <DIST>/lib/<jar>:<QUPATH_HOME>/lib/app/* WorkerMain
  --runtime-dir <RUNTIME_DIR>`; options on the command line; `DISPLAY`, `WAYLAND_DISPLAY` and JVM
  option variables removed.
- `qupath-script` (no separate Java runtime): `<QUPATH_LAUNCHER> script <bootstrap>
  --args=<jar> --args=<jar sha256> --args=<RUNTIME_DIR>`; options (including an explicit `-Xmx`)
  only through `JAVA_TOOL_OPTIONS`. The JVM splits that variable at white space without backslash
  escapes, so each option is quoted (`launch.json` field `java_tool_options_quoting`; a directory
  with a space otherwise stops the JVM). The bootstrap refuses a jar whose sha256 differs. The
  QuPath 0.7.0 Linux launcher can crash before the JVM starts (JDK-8380085); its `--version`
  preflight detects this.

The bundle `manifest.json` lists every member with size and sha256.

## Schema validator, canonical JSON and parity with R

`SchemaValidator` and `CanonicalJson`/`CanonicalJsonReader` implement the rules the R package
documents in `inst/schema/README.md`. JUnit runs the shared corpora directly from `inst/schema`
(`protocol/v1` and the annotatR capability vocabulary `annotatr-control/v1`): valid fixtures,
invalid fixtures with their expected `(path, keyword, schema_path)` sidecars, canonical vectors and
rejection vectors. `scripts/contract-parity.sh` compares R and Java on a seeded random corpus:

```sh
tools/bridge/scripts/contract-parity.sh --work-dir work/<area>/contract-parity [--seed N]
```

It exits with 0 when every check passed, 1 when one failed and 2 for usage or environment errors,
and writes `contract-parity-report.json` into the work directory. It needs Rscript with testthat,
pkgload, withr and jsonlite, a Java 25 JDK and a warm Gradle cache (or `--online`).

## Smoke tests

Both scripts take `JAVA_HOME`, `QUPFLOWR_QUPATH_HOME`, `QUPFLOWR_XVFB` and the other toolchain
variables from the caller's environment and use `dev/toolchain.env` only for unset ones. Both
scripts isolate every child process (`env -i`, HOME/XDG/TMPDIR/Java preferences inside the
work directory, no `DISPLAY=:0` or Wayland), signal only processes they started, and exit non-zero
on any failed assertion. They write `results.tsv` and a JSON report into the work directory.

```sh
tools/bridge/scripts/smoke-extension.sh --work-dir work/<area>/smoke-extension --display :90
tools/bridge/scripts/smoke-extension.sh --display :90 --simulate-missing-extension  # retry path
tools/bridge/scripts/smoke-worker.sh --work-dir work/<area>/smoke-worker
```

`smoke-extension.sh` starts Xvfb and QuPath with the Temurin launcher (`java -cp
"<QUPATH_HOME>/lib/app/*" qupath.QuPath`, JVM options from `QuPath.cfg`), installs the extension in
an isolated user directory (`PrefsSeed.java` seeds `userPath`), autostarts the bridge, checks
discovery files, health, capabilities, 401/403 cases, menu and token hygiene, and stops QuPath with
SIGTERM. `smoke-worker.sh` verifies the distribution and runs the `java` profile (end of input and
SIGTERM) and the `qupath-script` profile through QuPath's `script` command.
